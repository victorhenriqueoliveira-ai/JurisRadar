# ADR-003: Autenticação — NextAuth.js v5 (Auth.js) com Credentials Provider

## Status

Aceito

## Data

2026-08-02

## Contexto

O JurisRadar exige autenticação multi-usuário com sessões isoladas por conta. No MVP, contas são criadas administrativamente (sem autoregistro público). O sistema é Next.js full-stack hospedado na Vercel; a solução de auth deve integrar com App Router e Route Handlers sem fricção.

## Decisão

Adotar **NextAuth.js v5 (Auth.js)** com **Credentials Provider** (e-mail + senha com hash bcrypt) e **JWT sessions** armazenadas em cookie HTTP-only.

- NextAuth v5 foi reescrito para App Router nativamente, com middleware de proteção de rotas via `auth()` helper.
- Credentials Provider permite login com e-mail/senha sem dependência de OAuth externo.
- JWT sessions eliminam a necessidade de tabela de sessões no banco para o MVP — sessão validada a cada request via verificação do JWT.
- Usuários são criados diretamente no banco (`users` table) via script administrativo.

## Alternativas Consideradas

### Alternativa: Clerk

- **Descrição**: SaaS de auth com UI pré-construída, dashboard de gerenciamento de usuários, integração Next.js via SDK.
- **Prós**: Zero código de auth para escrever; dashboard administrativo para criar usuários; UI de login pronta.
- **Contras**: Dependência de serviço externo pago (tier gratuito limitado a 10k MAU — aceitável, mas cria lock-in); dados de usuários armazenados fora do sistema (complicação LGPD para produto jurídico).
- **Por que rejeitada**: Dados de usuários fora do controle do sistema cria preocupação LGPD; no MVP com poucos usuários administrativos, o overhead de Clerk não se justifica.

### Alternativa: Lucia Auth

- **Descrição**: Biblioteca minimalista de sessões type-safe, sem abstrações pesadas, integra com Drizzle ORM.
- **Prós**: Controle total sobre sessions; tipo-segura; sem opinião sobre provider.
- **Contras**: Requer implementar manualmente toda a lógica de sessão, refresh e middleware de proteção — mais código de infraestrutura para o MVP.
- **Por que rejeitada**: NextAuth v5 entrega o mesmo nível de controle com menos código de infraestrutura para o caso de uso de credentials simples.

## Consequências

### Positivas

- Middleware de proteção de rotas em `middleware.ts` com `auth()` cobre todos os endpoints e páginas em uma linha.
- JWT stateless reduz queries ao banco por request autenticado.
- Ecossistema maduro; bem documentado para Next.js App Router.

### Negativas

- JWT sessions não podem ser invalidadas antes do expiry sem uma blocklist no banco — para MVP validatório (sem logout forçado de emergência) é aceitável.
- Credentials Provider exige implementar hash de senha e seed de usuários manualmente (script de seed no `package.json`).

### Riscos

- NextAuth v5 ainda recebe breaking changes ocasionalmente (beta/stable em transição) — fixar a versão no `package.json` e revisar changelog antes de atualizar.

## Notas de Implementação

- Configurar em `src/auth.ts` com `providers: [Credentials({ ... })]`.
- Hash de senha com `bcryptjs` (sem módulo nativo, compatível com Edge).
- Middleware em `middleware.ts` na raiz do projeto com matcher excluindo `/login` e rotas públicas.
- Script de seed: `pnpm db:seed` cria usuários iniciais do MVP.
- Variáveis: `AUTH_SECRET` (gerado via `npx auth secret`).
