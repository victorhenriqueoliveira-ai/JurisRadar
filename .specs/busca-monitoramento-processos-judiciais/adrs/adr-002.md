# ADR-002: Banco de Dados e ORM — Neon (Postgres) + Drizzle ORM

## Status

Aceito

## Data

2026-08-02

## Contexto

O JurisRadar precisa de um banco de dados relacional para persistir usuários, estado dos jobs de busca federada, resultados de processos e cache com TTL. O sistema é hospedado na Vercel com funções serverless, o que impõe requisitos específicos ao cliente de banco: a conexão deve ser eficiente em cenários de cold start, e o ORM não pode introduzir latência de inicialização significativa por invocação.

## Decisão

Adotar **Neon** como provedor de Postgres gerenciado e **Drizzle ORM** como camada de acesso a dados.

- Neon oferece Postgres serverless com pooling de conexões nativo (`@neondatabase/serverless`) otimizado para ambientes sem estado (Vercel Functions), eliminando o problema de esgotamento de conexões comum com clientes Postgres tradicionais.
- Drizzle é type-safe, sem runtime pesado (sem engine binária), com inferência de tipos direta dos schemas — sem geração de código separada. Suporta migrations via `drizzle-kit`.

## Alternativas Consideradas

### Alternativa: Supabase (Postgres) + Prisma ORM

- **Descrição**: Supabase provê Postgres + auth integrado em um serviço; Prisma tem ecossistema maduro e migrações declarativas.
- **Prós**: Auth já incluso, dashboard administrativo, SDK de cliente para operações simples.
- **Contras**: Prisma Query Engine é uma biblioteca nativa que adiciona ~50ms de cold start em funções serverless; Supabase auth seria redundante com NextAuth.js v5 já adotado.
- **Por que rejeitada**: O custo de cold start do Prisma é incompatível com o modelo de invocação de funções do Inngest, onde cada step pode ser uma cold start separada.

### Alternativa: Vercel Postgres + Prisma

- **Descrição**: Vercel Postgres usa Neon internamente; Prisma como ORM.
- **Prós**: Integração nativa com Vercel Dashboard (provisioning automático).
- **Contras**: Mesmo problema de cold start do Prisma; Vercel Postgres é essencialmente Neon com markup de preço.
- **Por que rejeitada**: Custo maior sem vantagem técnica adicional sobre Neon direto.

## Consequências

### Positivas

- Conexões sem esgotamento em ambiente serverless graças ao `@neondatabase/serverless` com HTTP pooling.
- Drizzle schemas são TypeScript puro — tipos de tabela inferidos diretamente pelo compilador, sem passo de geração.
- Migrações via `drizzle-kit generate` + `drizzle-kit migrate` integram ao pipeline de CI/CD.
- Tier gratuito do Neon é suficiente para o MVP validatório.

### Negativas

- Drizzle tem API menos intuitiva que Prisma para consultas complexas (joins aninhados exigem mais verbosidade).
- Neon tem latência de "wake up" ocasional no tier gratuito após período de inatividade — aceitável para MVP, não para produção de alta disponibilidade.

### Riscos

- Migrações com Drizzle exigem disciplina: não há um `prisma migrate dev` interativo — mitigação via script de migrate no `package.json` documentado para o time.

## Notas de Implementação

- Usar `@neondatabase/serverless` com `neon()` driver via HTTP para compatibilidade com Edge Runtime.
- Schemas em `src/db/schema.ts`; migrações em `src/db/migrations/`.
- Variável de ambiente: `DATABASE_URL` (connection string Neon com pooler).
