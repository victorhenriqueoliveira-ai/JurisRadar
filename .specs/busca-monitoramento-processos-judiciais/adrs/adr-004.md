# ADR-004: Orquestração de Jobs Assíncronos — Inngest

## Status

Aceito

## Data

2026-08-02

## Contexto

A busca federada do JurisRadar consulta ~90 tribunais via DataJud em paralelo. Uma única requisição HTTP não pode encapsular esse processamento dentro dos limites de duração de função da Vercel (máximo 60s no plano Pro, 10s no Hobby por default). A solução precisa: (a) distribuir o processamento em múltiplas invocações, (b) persistir o progresso entre invocações, (c) garantir retries com backoff em caso de falha de tribunal, (d) ser observável (logs de cada step).

## Decisão

Adotar **Inngest** para orquestração dos jobs de busca federada.

Cada busca dispara um evento `search/created` no Inngest. A função Inngest `federated-search` processa os ~90 tribunais em lotes sequenciais de N tribunais por `step.run()`, onde cada step é uma invocação independente da Vercel Function — respeitando o limite de timeout por invocação. Inngest gerencia o estado, retries e o encadeamento dos steps automaticamente.

## Alternativas Consideradas

### Alternativa: Vercel Cron + state machine manual no banco

- **Descrição**: Cron da Vercel dispara a cada 1 minuto uma rota `/api/jobs/process` que pega o próximo job pendente no banco e processa um lote, salvando o progresso.
- **Prós**: Sem dependência adicional; toda a lógica vive no código da aplicação.
- **Contras**: Latência mínima de 1 minuto entre lotes (granularidade do Cron); sem retries automáticos por step; estado da state machine inteiramente manual (flags no banco, lógica de locking para evitar processar o mesmo job duas vezes); sem observabilidade nativa de steps.
- **Por que rejeitada**: A granularidade de 1 minuto entre lotes tornaria uma busca de 90 tribunais (6 lotes de 15) levar no mínimo 6 minutos — inaceitável para a UX de progresso em tempo real.

### Alternativa: Self-calling Route Handler (fire-and-forget)

- **Descrição**: A rota de processo, após completar um lote, faz `fetch()` para si mesma (fire-and-forget) para processar o próximo lote.
- **Prós**: Sem serviço externo; implementação simples.
- **Contras**: `fetch` fire-and-forget não tem garantia de entrega; sem retries em caso de falha; a Vercel pode cancelar a invocação pai antes de a invocação filha iniciar; sem visibilidade de execução.
- **Por que rejeitada**: Arquitetura frágil sem garantia de entrega — incompatível com o critério de sucesso do MVP (zero erros de timeout não tratados).

### Alternativa: Trigger.dev

- **Descrição**: Alternativa ao Inngest com modelo similar de step functions serverless para Next.js.
- **Prós**: Tier gratuito; suporte a Next.js; step functions com retries.
- **Contras**: Menor adoção que Inngest no ecossistema Next.js; documentação menos madura; SDK com breaking changes mais frequentes.
- **Por que rejeitada**: Inngest tem integração mais madura com Next.js App Router e documentação mais ampla para o padrão de uso do JurisRadar.

## Consequências

### Positivas

- Cada `step.run()` é uma invocação independente da Vercel Function — o timeout por step é respeitado sem afetar os outros steps.
- Retries com backoff exponencial configuráveis por step, nativamente.
- Dashboard Inngest exibe o estado de cada job e cada step em tempo real — observabilidade sem instrumentação adicional.
- Tier gratuito do Inngest cobre o volume do MVP validatório.
- A mesma infraestrutura serve para o agendamento periódico da Fase 3 (Inngest cron triggers).

### Negativas

- Dependência de serviço externo: se o Inngest estiver indisponível, novos jobs não são processados — mitigação via timeout de polling no frontend (aviso ao usuário após N segundos sem progresso).
- Adiciona `INNGEST_EVENT_KEY` e `INNGEST_SIGNING_KEY` às variáveis de ambiente.
- Debugging de step functions exige familiaridade com o dashboard Inngest (curva de aprendizado inicial).

### Riscos

- Tamanho de lote por step precisa ser calibrado empiricamente: muito grande → timeout da Vercel Function; muito pequeno → muitos steps → latência total alta. Valor inicial sugerido: 10 tribunais por step.
- Inngest requer que a rota `/api/inngest` seja pública (sem auth middleware) — garantir que o middleware do NextAuth exclua essa rota do matcher.

## Notas de Implementação

- Instalar: `inngest` + `@inngest/next`.
- Rota Inngest em `src/app/api/inngest/route.ts` (excluída do middleware de auth).
- Função principal em `src/inngest/federated-search.ts`.
- Evento de trigger: `{ name: "search/created", data: { searchId, filters } }`.
- Cada step processa 10 tribunais em `Promise.allSettled()` — tribunais que falham são registrados em `failedTribunals` sem abortar o job.
- Variáveis: `INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`.
