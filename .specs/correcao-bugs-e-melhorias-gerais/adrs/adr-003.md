# ADR-003: Polling do Dashboard via Rota /api/dashboard/summary

## Status

Aceito

## Data

2026-08-21

## Contexto

O dashboard é atualmente um Server Component com Suspense — não possui mecanismo de atualização automática. Para implementar o auto-refresh de 30s após sync OAB, é necessário um mecanismo de polling client-side. Três abordagens foram avaliadas.

## Decisão

Criar a rota `GET /api/dashboard/summary` que retorna os mesmos dados de `aggregateDashboard()` e `getPrazosUrgentes()` em JSON. O dashboard recebe um Client Component de polling (`DashboardPoller`) que chama essa rota via `setInterval` + `visibilitychange`, atualizando o estado local sem recarregar a página inteira.

## Alternativas Consideradas

### Alternativa 1: router.refresh() a cada 30s

- **Descrição**: Client Component wrapper chama `router.refresh()` periodicamente, reaproveitando o Server Component existente.
- **Prós**: Menor mudança; mantém Server Component intacto.
- **Contras**: `router.refresh()` recarrega toda a árvore do Server Component, incluindo layout — causa flash visual indesejável e é mais pesado que um fetch pontual.
- **Por que rejeitada**: UX inferior com re-render visível da página inteira a cada 30s.

### Alternativa 2: Converter KPIs para Client Components com fetch direto

- **Descrição**: Cada card de KPI vira um Client Component que faz fetch da própria rota.
- **Prós**: Granularidade máxima no polling.
- **Contras**: Múltiplas requisições paralelas (uma por card); dispersa a lógica de polling; mais código para manter.
- **Por que rejeitada**: Overhead de N requisições por ciclo de polling desnecessário.

## Consequências

### Positivas

- Uma única requisição por ciclo de polling — eficiente.
- Server Component original pode ser mantido para o carregamento inicial (SSR).
- `DashboardPoller` é isolado e fácil de remover ou substituir.
- Polling pausado quando aba perde foco (`visibilitychange`) — sem requisições desnecessárias.

### Negativas

- Requer nova rota de API (`/api/dashboard/summary`).
- Parte do dashboard precisa de estado React no cliente para exibir dados atualizados.

### Riscos

- Se `aggregateDashboard()` for lenta, cada tick de 30s pode gerar query pesada — mitigar com cache de 15s na rota de API (`next: { revalidate: 15 }`).

## Notas de Implementação

- A rota `/api/dashboard/summary` deve reusar diretamente `aggregateDashboard()` e `getPrazosUrgentes()` de `src/services/dashboard.ts`.
- O `DashboardPoller` usa `useEffect` + `setInterval` com cleanup, e `document.addEventListener('visibilitychange')` para pausar quando `hidden`.
- O intervalo padrão é 30s, configurável via `NEXT_PUBLIC_DASHBOARD_POLL_INTERVAL_MS`.
- Dados iniciais são passados como props do Server Component para o `DashboardPoller` — sem loading state no primeiro render.
