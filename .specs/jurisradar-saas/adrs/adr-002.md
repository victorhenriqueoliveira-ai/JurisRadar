# ADR-002: Multi-tenancy com Row-Level Isolation via org_id

## Status

Aceito

## Data

2026-08-19

## Contexto

O JurisRadar SaaS precisa isolar dados de processos, notificações, financeiro e calendário por escritório. O banco atual usa PostgreSQL (Neon serverless) com Drizzle ORM e não tem nenhum conceito de tenant. A escolha da estratégia de multi-tenancy afeta o schema inteiro, as migrations e todas as queries da aplicação.

## Decisão

Adotar row-level isolation: todas as tabelas de domínio recebem uma coluna `org_id` (UUID, NOT NULL, FK para `organizations`). O `org_id` é sempre derivado da sessão autenticada — nunca aceito do request body. Um helper `requireOrgId(session)` centraliza a extração e lança `UnauthorizedError` se ausente. Todas as queries passam `eq(table.orgId, orgId)` obrigatoriamente.

## Alternativas Consideradas

### Alternativa B: Schema-per-tenant no PostgreSQL

- **Descrição**: Cada escritório tem seu próprio PostgreSQL schema (`org_abc.processos`, `org_abc.usuarios` etc.)
- **Prós**: Isolamento mais forte a nível de banco; migrations podem ser feitas por tenant individualmente.
- **Contras**: Drizzle ORM não suporta schema dinâmico nativamente; migrations precisam ser aplicadas em cada schema separadamente; pooling de conexões com Neon serverless fica muito mais complexo; impraticável acima de 100 tenants.
- **Por que rejeitada**: Incompatível com Drizzle + Neon sem engenharia custom significativa.

### Alternativa C: Banco separado por tenant

- **Descrição**: Cada escritório tem seu próprio banco PostgreSQL.
- **Prós**: Isolamento máximo; backup e restore por tenant; compliance mais simples.
- **Contras**: Impraticável operacionalmente para SaaS com centenas de clientes; custo de infra cresce linearmente; Neon não tem API de provisionamento dinâmico de bancos adequada para isso.
- **Por que rejeitada**: Inviável economicamente e operacionalmente para a escala inicial.

## Consequências

### Positivas

- Zero overhead de infra adicional.
- Migrations simples: Drizzle aplica em uma única base.
- Performance aceitável com índices em `org_id` em cada tabela.
- Todas as queries já estruturadas para escalar horizontalmente se necessário.

### Negativas

- Exige disciplina: qualquer query esquecida de filtrar por `org_id` vaza dados entre tenants.
- Não há isolamento a nível de banco; um bug crítico pode potencialmente expor dados de múltiplos tenants simultaneamente.

### Riscos

- **Vazamento de dados por query sem filtro**: Mitigação — helper `withOrgFilter(query, orgId)` obrigatório em todos os repositories; testes de isolamento automatizados que verificam que um tenant não consegue acessar dados de outro.

## Notas de Implementação

- Adicionar coluna `org_id uuid NOT NULL references organizations(id)` em: `processos`, `movimentacoes`, `notificacoes`, `honorarios`, `pagamentos`, `eventos_calendario`, `notas_processo`, `membros_escritorio`, `searches`, `searchResults`.
- Criar índice composto `(org_id, created_at DESC)` nas tabelas de alta leitura.
- Middleware de sessão deve popular `session.user.orgId` no JWT para evitar round-trip ao banco em cada request.
