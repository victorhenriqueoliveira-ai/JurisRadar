# ADR-005: Inngest para Worker de Monitoramento de Processos

## Status

Aceito

## Data

2026-08-19

## Contexto

O JurisRadar SaaS precisa de um worker que sincronize processos de cada advogado periodicamente (padrão: 1x ao dia) e detecte novas movimentações para disparar notificações. O projeto já usa Inngest para o cron diário de download dos PDFs do DJe TJSP. A decisão é expandir o uso do Inngest ou adotar uma solução diferente para o novo worker.

## Decisão

Expandir o uso do Inngest para o monitoramento de processos. Criar duas funções Inngest: (1) `sync-processos-scheduler` — cron diário que emite um evento `processos/sync.requested` por advogado ativo; (2) `sync-processos-worker` — handler do evento, que consulta DataJud + PJe, compara com o estado salvo, persiste movimentações novas e emite `notificacao/nova` para cada evento relevante detectado.

## Alternativas Consideradas

### Alternativa B: Vercel Cron + API Routes

- **Descrição**: Cron definido em `vercel.json` que chama uma API Route Next.js.
- **Prós**: Zero dependência externa; configuração simples.
- **Contras**: Timeout de 60s no Vercel Pro (10s no Hobby); sem retry automático em falha; sem observabilidade nativa; para 500 escritórios com 80 processos cada, uma única API Route não consegue processar tudo em 60s.
- **Por que rejeitada**: Limitações de timeout inaceitáveis para sincronização de centenas de escritórios.

### Alternativa C: Serviço separado (Node.js worker)

- **Descrição**: Microserviço dedicado rodando em servidor próprio (ex.: VPS ou container).
- **Prós**: Controle total de execução, sem timeout, sem dependência de terceiro.
- **Contras**: Infra adicional para provisionar, monitorar e manter; deploy separado; custo adicional.
- **Por que rejeitada**: Overhead operacional injustificado quando o Inngest já resolve o problema sem infra extra.

## Consequências

### Positivas

- Retry automático em falha com backoff exponencial — nenhum sync perdido silenciosamente.
- Dashboard Inngest mostra histórico de execuções, erros e tempo por função.
- Fan-out natural: o scheduler emite um evento por advogado, o worker processa em paralelo sem coordenação manual.
- Sem timeout de execução — Inngest usa step functions que pausam e retomam entre etapas.

### Negativas

- Dependência de terceiro (Inngest Cloud) para funcionalidade crítica.
- Plano gratuito do Inngest tem limite de 50k eventos/mês — com 500 escritórios e sync diário = ~15k eventos/mês (dentro do limite); plano pago necessário se crescer.

### Riscos

- **Inngest indisponível**: Mitigação — sync manual via botão no CRM (chama API Route diretamente sem Inngest) como fallback; alertas de monitoramento no Inngest Dashboard.

## Notas de Implementação

Funções Inngest a criar em `src/inngest/`:
- `sync-processos-scheduler.ts`: `cron("0 3 * * *")` (3h BRT) — busca advogados ativos, emite `processos/sync.requested` por advogado.
- `sync-processos-worker.ts`: handler de `processos/sync.requested` — steps: (1) buscar processos no DataJud por OAB, (2) buscar no PJe/Comunica, (3) diff com `ultimaMovimentacao` salva, (4) persistir novas movimentações, (5) emitir `notificacao/nova` por evento relevante.
- `notificacao-dispatcher.ts`: handler de `notificacao/nova` — persiste notificação in-app + enfileira e-mail via Resend.
