ADR-002: Mecanismo de Busca Full-Text — tsvector com Dicionário Português

## Status

Aceito

## Data

2026-08-07

## Contexto

A busca por palavra-chave é o núcleo da feature de DJE/TJSP. O banco de dados já é Neon Postgres, que suporta nativamente três mecanismos de busca textual sem extensões externas: tsvector com configuração de idioma, pg_trgm (trigramas) e ILIKE simples.

O volume esperado é expressivo: os Cadernos 2 e 3 do TJSP somam potencialmente dezenas de milhares de publicações por mês. O texto das publicações é em português, com termos jurídicos específicos que envolvem variação morfológica ("alimentos", "alimentícia", "alimentar" são o mesmo conceito para o advogado).

## Decisão

Usar `tsvector` com configuração de idioma `'portuguese'`, coluna gerada automaticamente (`GENERATED ALWAYS AS ... STORED`), indexada com GIN. A busca usa `plainto_tsquery('portuguese', $term)` para processar o input do usuário sem necessidade de sintaxe especial. Os snippets de resultado são gerados pela função `ts_headline` do próprio Postgres.

```sql
ALTER TABLE dje_publications
  ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (to_tsvector('portuguese', content)) STORED;

CREATE INDEX dje_publications_search_vector_idx
  ON dje_publications USING GIN(search_vector);

-- Busca:
SELECT
  id, process_number, instance, court,
  publication_date, caderno,
  ts_headline(
    'portuguese', content,
    plainto_tsquery('portuguese', $1),
    'MaxWords=50, MinWords=20, StartSel=<mark>, StopSel=</mark>'
  ) AS snippet
FROM dje_publications
WHERE search_vector @@ plainto_tsquery('portuguese', $1)
  AND publication_date BETWEEN $2 AND $3
ORDER BY publication_date DESC
LIMIT $4 OFFSET $5;
```

## Alternativas Consideradas

### Alternativa: pg_trgm (trigramas)

- **Descrição**: índice GIN com `gin_trgm_ops`, busca via ILIKE ou `%` com similaridade
- **Prós**: funciona bem para termos exatos e parciais; tolerante a erros de digitação; zero configuração de idioma
- **Contras**: sem redução morfológica — "alimentos" e "alimentícia" são considerados diferentes; índice maior que tsvector; sem função nativa de snippet
- **Por que rejeitada**: texto jurídico em português exige correspondência semântica por radical — "pensão alimentícia" deve encontrar publicações com "alimentos" e "alimentar"

### Alternativa: ILIKE simples

- **Descrição**: `WHERE LOWER(content) LIKE LOWER('%termo%')` sem índice especializado
- **Prós**: zero configuração; fácil de implementar
- **Contras**: full-scan na tabela sem índice → inviável em volume de dezenas de milhares de linhas; sem ranking de relevância; sem snippet nativo
- **Por que rejeitada**: não atende ao requisito de desempenho (< 5 segundos para qualquer período disponível)

## Consequências

### Positivas

- Redução morfológica em português: "alimentar", "alimentícia", "alimentos" → mesma raiz, mesmo resultado
- `ts_headline` gera snippets com highlighting diretamente no Postgres, sem processamento adicional no Node.js
- Coluna `GENERATED ALWAYS AS STORED` — o índice é mantido automaticamente pelo Postgres a cada INSERT, sem trigger manual
- GIN index é ideal para tsvector: consultas em O(log n) independentemente do volume

### Negativas

- Busca exata por número CNJ parcial não funciona via tsvector — números são tokenizados; para busca por número de processo, usar filtro separado com índice `btree` em `process_number`
- Termos com grafia técnica muito específica (siglas, jargões latinos como "in limine") podem não ter stemming ideal no dicionário português do Postgres
- Coluna gerada aumenta o tamanho em disco da tabela

### Riscos

- O dicionário `portuguese` da instalação do Postgres deve estar disponível no Neon — verificar na primeira migration
- Se o conteúdo extraído do PDF contiver caracteres corrompidos ou encoding incorreto, o tsvector pode gerar lixo — mitigar com limpeza de texto antes do INSERT

## Notas de Implementação

- Adicionar `LANGUAGE = 'portuguese'` explicitamente em toda chamada `to_tsvector` e `plainto_tsquery` para evitar fallback para `'simple'` (sem stemming)
- `ts_headline` deve ser chamado apenas nas linhas do resultado final (após LIMIT/OFFSET), não antes, para evitar processamento desnecessário
- Índice adicional `btree` em `publication_date` é obrigatório para o filtro de período, pois o GIN do tsvector não ajuda no range de datas
